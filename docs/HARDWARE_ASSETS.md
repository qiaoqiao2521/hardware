更新日期：2026-10-06（Asia/Shanghai）。

本档案集中列举已讨论的硬件、仓库已有实体设备快照和实验工程，作为后续补充规格、接口、用途、故障与项目安排的入口。当前优先完成清单；未确认的在手状态、数量和规格保留为“待核实”。本轮依据已有记录整理，没有连接设备重新体检。

## 记录依据

| 标记 | 含义 | 使用边界 |
|---|---|---|
| 历史体检 | 已有带日期的系统枚举或检查报告 | 只说明检查当时的设备与功能状态 |
| 对话提及 | 原讨论或上一位助手的总结中出现 | 不据此确认在手、准确规格、数量或功能通过 |
| 工程存在 | 仓库保存了代码或接线工程 | 不据此确认实物在手或数量 |
| 官方能力 | 厂商或软件官方文档描述的支持范围 | 不等于用户这台设备已经验证可用 |
| 待核实 | 尚缺设备身份、原始记录或实测 | 保留字段，后续收到证据再更新 |

临时编号只用于连接档案与后续记录，不能用于统计实物总数。J1900 的“多台”“触摸款”等描述可能互有重合；目前仅将有独立报告的 B68TK 触摸机明确列为一个历史实例。

## 性能比较与选型口径

上一位助手总结了两条筛选口径：“所有设备必须和N100比”“常规设备原则上不能低于J1900”。本轮读到的原会话仅有四个可读取回合，未找到这两条的用户原话，因此保留为继承口径，适用范围待后续确认。暂不把未测设备判为合格或不合格。

| 比较维度 | 记录内容 | 当前证据状态 |
|---|---|---|
| CPU | 同版本程序、相同数据量的完成时间；记录线程与功耗策略 | 未建立同口径N100/J1900对照；全部待测 |
| 视频解码 | 相同摄像头编码、分辨率与路数；掉帧、CPU占用、解码器 | GPU/VPU参数与摄像头解码实测分别记录 |
| AI推理 | 相同模型、输入、量化与检测频率；推理延迟与资源占用 | TOPS不能替代模型实测，也不能证明准确率 |
| 准确率 | 同一录像与人工标注的漏报、误报、事件延迟 | 用户原话“我的yolo识别不高”；尚无量化基线 |
| I/O与功耗 | 实际引出的网口/串口/存储、待机与目标负载功耗、温升 | B68TK已枚举部分接口，其余逐台待核实 |

## 监控与家庭自动化规划

当前拟议结构为“海康NVR/摄像头提供视频 → Frigate检测与事件录像 → Home Assistant联动与通知”。ROCK 5C优先作为Frigate试验候选；空闲且满足安装条件的J1900或Pi 5作为HAOS候选。这是规划，不是已部署状态。详细步骤与验收条件见[监控项目计划](FRIGATE_HAOS_PLAN.md)。

现有YOLO的识别问题要保留为独立目标。Frigate的区域检测与目标跟踪流程值得比较，但更换软件不能保证准确率提高。
